# Sims 4 tooling: creation, management and repair
Reviewed 2026-11-14. Source research, not a benchmark, install approval, compatibility certificate or finished integration.

## Existing Foundry work comes first
Main at `1b94fde4603ccfefd073927b727b48884e287634` is a sparse bootstrap/documentation tree, but the project is not empty. [Open PR #6](https://github.com/Herbertofury/Sims4Foundry/pull/6), head `9761ff51b949689d2c7845dc27908c300cdb33f0`, already supplies a Python CLI foundation. Its [README](https://github.com/Herbertofury/Sims4Foundry/blob/9761ff51b949689d2c7845dc27908c300cdb33f0/tooling/game-cli/README.md) and implementation were inspected, not executed in this research pass.

Existing work includes bounded DBPF 2.1 resource-index inspection, exact TGI overlap reporting, stored-resource diffs, bounded ZIP/CRC checks for script archives, Python bytecode-header reporting without importing code, hash-verified external staging, expiring plans, receipts and exclusive locks. The inspected package reader does not decompress or semantically decode every resource. TGI overlap is a candidate conflict, not proof of incompatibility or permission to merge files. Process/window observation and pinned capture helpers are not qualified semantic game control.

Several later feature branches exist, including profile receipts and retained process witnesses. Preserve them and reconcile their ownership before implementation. Do not merge PR #6 as a live-control release: its own acceptance gate remains game-qualified adapter work. No Apex work, game launch, save mutation, payload reconstruction or recovery workflow was performed here.

## Official creation route and repair limits
EA's [Maker Program and Marketplace](https://www.ea.com/games/the-sims/the-sims-4/news/the-sims-maker-program-and-marketplace) describes an approved-maker creation route and Maker Suite. Treat it as a separate eligible-user workflow, not an open-source SDK or unrestricted API. No account enrollment, terms acceptance or marketplace submission is included here. Check [EA mod policy](https://help.ea.com/en/articles/the-sims/the-sims-4/mods-policy/) separately for outside-program distribution.

Use [EA's mod/update troubleshooting](https://help.ea.com/en/articles/the-sims/the-sims-4/mods-and-the-sims-4-game-updates/) for creator compatibility checks and controlled isolation. Foundry should explain suspected problems, not promise universal automatic repair. Work on copied profiles/saves; never overwrite a valued save after removing CC for diagnosis. Cache removal is not proof that a broken script or mesh was repaired.

## First implementable evaluation and backlog
1. **Preserve the baseline:** inventory latest branches, tests and ownership; extract reusable read-only scanner interfaces instead of another standalone parser. Existing receipts and hash-pinned staging remain the safety baseline.
2. **Reader comparison:** run existing Python, LlamaLogic and S4TK against the same small licensed real-file corpus plus malformed fixtures. Record exact commits, game build, supported TGI classes, compressed/unknown handling, output identities, cold/warm p50/p95 time, peak memory and failures. No generated microbenchmark alone proves target improvement.
3. **Diagnostics contract:** versioned local JSON for file SHA-256, TGI, provenance, evidence timestamp, game-build range, dependency and confidence. Separate corruption, duplicate bytes, same-TGI overlap, missing dependency, stale script version and unknown compatibility. No inferred “safe to delete.”
4. **Reversible edits:** write to a new destination, validate/reopen, prove unaffected resource preservation, retain original and manifest; atomic replacement only after explicit scope and rollback are verified. Do not silently batch-fix unsupported types.
5. **Management:** source registry with exact author URL and permitted update route, last-good status, interrupted-download recovery and explicit authentication-required state. Browser login does not grant API access. Never export cookies or private/paywalled content into public fixtures.
6. **Creation:** prioritize STBL/tuning read-preview-validate round trips, then licensed CAS/mesh/texture adapters. Treat rig/animation preservation and game rendering as separate acceptance gates. Do not displace active External-CAS/Apex implementations.
7. **Report interoperability first:** compare an inert Better Exceptions-style report import with existing diagnostics using synthetic sanitized reports before handling user reports. Strip usernames, local paths, save identities and private URLs from exported evidence.
8. **Acceptance:** retain raw comparisons and failed evidence. Unit/schema success, real public fixture tests, authenticated tests, game acceptance and release delivery are distinct statuses.

No tools were installed, no upstream code or game assets were copied, and no game compatibility/performance claim was validated in this research pass. S4Studio availability, unverified reuse licenses and real-game qualification remain explicit evaluation gates, not reasons to discard independent read-only work.
